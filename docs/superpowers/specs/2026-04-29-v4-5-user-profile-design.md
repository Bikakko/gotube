# GoTube V4.5.0 用户昵称与自助改密设计

## 1. 目标

V4.5.0 只解决两个明确问题：

1. 登录账号与对外显示名目前是同一个字段，用户管理、分享归属、后台列表都不够自然。
2. 普通用户缺少自助修改密码能力，当前只能依赖管理员或重建账号。

本轮不重做认证体系，不引入邮箱、手机号、找回密码、多因素认证，也不开放修改登录账号。目标是用最小兼容改动，把“账号”与“昵称”拆开，并补上“普通用户本人改密码”这条基础能力。

## 2. 范围

### 2.1 本轮包含

- 为所有用户新增昵称字段。
- 登录继续只使用账号，不接受昵称登录。
- 注册、管理员创建用户、管理员编辑用户时支持设置昵称。
- 普通用户和管理员都能修改自己的昵称。
- 普通用户支持自助修改密码。
- 管理员继续保留“无旧密码修改其他用户密码”的现有能力。
- 普通用户修改密码成功后，当前用户全部登录 Token 失效，要求重新登录。
- 用户管理页继续以数字 `ID` 作为第一列展示。

### 2.2 本轮不包含

- 修改登录账号。
- 忘记密码 / 找回密码。
- 邮箱、手机号、短信验证。
- 多终端会话管理界面。
- 昵称历史记录。
- 按昵称模糊登录。
- 管理员本人在页面内修改自己的密码。

## 3. 核心设计

### 3.1 字段拆分

保留现有 `users.username` 作为登录账号，新增两列：

- `display_name`
  - 用户昵称，页面展示优先使用它。
- `display_name_key`
  - 昵称归一化键，只用于搜索、排序和一致性处理，不直接展示。

这样可以避免把现有 `username` 语义整体翻转，认证、Token、管理员同步逻辑也无需整体改造。

### 3.2 昵称规则

昵称不是完全任意字符串。为了兼容多语言展示，又避免注入和控制字符问题，规则定为：

- 长度：`2-32`
- 允许：
  - 中文
  - 日文
  - 韩文
  - 英文字母大小写
  - 数字
  - 空格
  - `_ - .`
- 禁止：
  - 控制字符
  - 换行、制表
  - HTML 敏感字符：`< > " ' \``
  - 路径/转义敏感字符：`/ \`
- 入库前统一处理：
  - 去掉首尾空格
  - 连续空格压缩为单个空格

昵称不要求唯一。`display_name_key` 继续保留，用于：

- 搜索时的归一化匹配
- 列表排序一致性
- 后续扩展时避免把展示值和处理值混在一起

这套规则允许中日韩文字，同时把高风险符号排除在外，足够覆盖昵称场景。

### 3.3 老用户迁移

升级时对现有用户自动回填：

- `display_name = username`
- `display_name_key = normalize_display_name(username)`

这样升级后：

- 不会出现空昵称。
- 老前端如果短时间内仍读取旧字段，行为也不会立刻坏掉。
- 管理员和普通用户都能在后续再自行改昵称。

## 4. 数据层设计

### 4.1 数据库变更

`users` 表新增：

- `display_name VARCHAR(64) NOT NULL DEFAULT ''`
- `display_name_key VARCHAR(96) NOT NULL DEFAULT ''`

考虑 SQLite 现状，本轮继续沿用轻量迁移方式：

1. 检查列是否存在，不存在则 `ALTER TABLE`
2. 回填历史数据
3. 为 `display_name_key` 建普通索引

### 4.2 索引处理

本轮不对昵称建立唯一约束。`display_name_key` 只建立普通索引，用于后台搜索和后续扩展。

## 5. 后端接口设计

### 5.1 响应结构扩展

所有返回用户信息的接口统一补充：

- `display_name`

`username` 继续保留，作为登录账号和后台运维标识。

前端展示规则统一为：

- 优先展示 `display_name`
- 必要时附带较弱样式展示 `username`

### 5.2 注册接口

`POST /api/auth/register`

新增请求字段：

- `display_name`

校验顺序：

1. 校验账号
2. 校验密码
3. 校验邀请码
4. 校验昵称合法性

### 5.3 管理员用户管理接口

涉及：

- 创建用户
- 更新用户
- 用户列表响应

新增或返回：

- `display_name`

管理员编辑用户时：

- 可以修改昵称
- 继续保留当前“管理员无旧密码修改其他用户密码”的能力

### 5.4 当前用户资料接口

新增一个“当前用户资料更新”接口，建议：

- `PATCH /api/me/profile`

请求体只包含：

- `display_name`

这样昵称修改不必借道管理员接口，也不会把“本人资料修改”和“管理员改用户”混在一起。

### 5.5 当前用户修改密码接口

新增：

- `POST /api/me/password`

请求体：

- `old_password`
- `new_password`

规则：

- 必须先验证旧密码
- 新密码长度 `6-64`
- 新密码不能全空格
- 新旧密码不能相同

成功后：

- 将该用户所有 `auth_tokens.is_active` 置为 `false`
- 返回成功消息
- 前端收到后清理本地登录态并跳回登录入口

该接口只对普通用户开放。管理员本人不使用该接口，因为管理员密码来源于 `.env` 配置同步；如果允许页面内修改，会在下一次服务启动或同步时被配置覆盖，形成伪能力。

## 6. 认证与安全设计

### 6.1 Token 失效策略

普通用户改密码成功后，不保留当前会话，直接废掉当前用户全部 Token。

原因：

- 逻辑简单
- 行为清晰
- 安全边界明确
- 不需要额外区分“当前设备”和“其他设备”

### 6.2 输入安全

昵称的主要风险不是 SQL 注入，而是：

- 前端展示时的 HTML 注入
- 搜索或筛选时的特殊字符干扰
- 路径/日志输出污染

因此本轮要求：

1. 服务端做严格昵称校验与归一化。
2. 前端继续只用 `textContent` 渲染昵称，不拼 `innerHTML`。
3. 管理页、下载页、首页若出现昵称，统一走文本节点输出。

## 7. 前端设计

### 7.1 登录

登录页不改交互语义，仍然明确提示：

- 使用账号登录

不增加昵称登录入口，避免用户混淆。

### 7.2 注册

注册表单增加：

- 昵称

顺序建议：

1. 账号
2. 昵称
3. 密码
4. 邀请码

昵称提示文案应强调：

- 这是展示名，不是登录账号

### 7.3 用户展示

所有登录后展示用户身份的位置，统一改为同时显示：

- 账号
- 昵称
- ID

涉及页面：

- 下载页用户状态
- 管理页用户列表
- 管理页媒体拥有者信息
- 可能返回当前用户资料的前端面板

其中管理页用户列表继续保持：

1. `ID`
2. `账号`
3. `昵称`

`ID` 为纯数字内部标识，继续作为第一列。其余登录后身份展示区域也不再做“按需隐藏”，统一保持三项可见，便于后台排查和用户对应。

### 7.4 修改资料

在当前用户可访问的设置区增加两个独立动作：

1. 修改昵称
2. 修改密码

不建议做成一个混合表单。两者语义和校验完全不同，拆开更清楚，也更容易给出准确提示。

其中“修改密码”入口只对普通用户展示；管理员显示配置说明，不显示可提交表单。

## 8. 文案约定

### 8.1 账号与昵称

页面文案必须明确区分：

- 账号：用于登录，不对外展示为主
- 昵称：用于显示，不用于登录

避免出现“用户名”同时指代两者的情况。后台可统一采用：

- 账号
- 昵称

### 8.2 修改密码反馈

成功文案建议：

- `密码已更新，请重新登录。`

失败文案示例：

- `当前密码不正确。`
- `新密码长度需为 6 到 64 位。`
- `新密码不能与当前密码相同。`

### 8.3 管理员密码说明

- `管理员密码由服务器配置管理，请在部署配置中更新。`

## 9. 测试与验收

### 9.1 后端测试

至少覆盖：

1. 老用户迁移后自动拥有昵称
2. 中日韩昵称可通过校验
3. 危险字符昵称被拒绝
4. 当前用户改昵称成功
5. 普通用户改密码时旧密码错误被拒绝
6. 普通用户改密码成功后全部 Token 失效
7. 管理员本人不显示自助改密入口

### 9.2 前端验收

至少验证：

1. 登录仍然只能用账号
2. 注册时昵称可填且提示清晰
3. 管理员与普通用户都能看到昵称
4. 管理页用户列表第一列继续显示数字 ID
5. 修改昵称后页面刷新仍正确显示
6. 普通用户改密码成功后被强制退出并要求重新登录
7. 管理员界面不提供本人改密表单

## 10. 实施顺序

1. 数据库迁移与数据回填
2. 用户模型与响应模型扩展
3. 注册 / 用户管理 / 当前用户资料接口改造
4. 普通用户改密码接口
5. 前端用户展示与表单调整
6. 回归测试与手工验收

## 11. 验收标准

V4.5.0 完成后，应满足：

1. 所有用户同时拥有“账号”和“昵称”，昵称可重复。
2. 登录只接受账号，不接受昵称。
3. 管理员和普通用户都能修改自己的昵称。
4. 普通用户能修改自己的密码。
5. 管理员继续通过现有能力修改其他用户密码，但本人密码不走页面内修改。
6. 普通用户改密码成功后，旧登录态全部失效。
7. 昵称支持中日韩及常见字母数字组合，但危险字符被拒绝。
8. 管理页用户列表第一列继续显示数字 ID。

# GoTube V5.0.0 门户首页与 NinLucky 接入设计

## 背景

GoTube V4.x 已完成多用户视频库、邀请码、后台管理台与运维收口。下一阶段不再只是扩展下载业务，而是把站点升级为统一入口站。

V5.0.0 的首要变化是：

- 根路径 `/` 不再是空白页或单业务入口；
- 首页升级为应用门户；
- 首批承载两个入口：
  - `GoTube`
  - `您吉祥`
- 为后续继续增加入口预留统一结构；
- `您吉祥` 对应独立 GameHub 项目，保留独立仓库、独立构建、独立后端。

## 目标

在不破坏现有 GoTube 下载、分享、后台功能的前提下，把 GoTube 主站升级为统一应用入口，并以 `/ninlucky/` 路径接入“您吉祥”游戏平台。

## 非目标

本阶段不做以下事项：

- 不把 GameHub 前后端并入 GoTube 仓库；
- 不共用 GoTube 与 GameHub 数据库；
- 不让 GameHub 直接读写 GoTube 业务表；
- 不在 V5.0.0 一开始就做多入口后台管理系统；
- 不修改 GoTube 原有隐藏下载入口、后台入口和分享入口的语义。

## 版本定位

V5.0.0 是产品形态升级版本，不是单点修补版本。变化点在于：

- 站点首页角色变化；
- 多应用入口结构确立；
- 独立业务接入边界确立；
- 统一身份体系开始服务站点级入口。

## 信息架构

### 一级入口

V5.0.0 首版门户包含两个一级应用入口：

1. `GoTube`
2. `您吉祥`

首页必须以“应用入口”而不是“说明文字”为主，后续新增入口时应能复用同一数据结构和渲染逻辑。

### 路由结构

推荐最终路由如下：

- `/`：门户首页
- `/{hidden_path}`：GoTube 下载页
- `/{hidden_path}/admin`：GoTube 管理后台
- `/watch`：GoTube 分享播放页
- `/ninlucky/`：您吉祥 GameHub

说明：

- `/ninlucky/` 是技术路由；
- “您吉祥”是展示名称；
- 技术路径与展示名称分离，便于未来品牌文案调整而不影响部署与链接稳定性。

## 业务边界

### GoTube 负责什么

- 门户首页和入口展示；
- 用户体系、登录、注册、邀请码；
- 原有下载、分享、后台管理；
- 站点级导航与入口组织；
- 给外部应用提供统一身份校验基础。

### GameHub 负责什么

- 游戏列表、启动器、主题、通知；
- 成绩提交、排行榜、统计；
- 游戏平台自身数据库；
- 游戏平台自身前后端构建与运行。

### 明确不共享的内容

- 不共享业务数据库；
- 不共享成绩表；
- 不共享视频库；
- 不共享下载任务和 Cookie 管理逻辑；
- 不共享运维脚本内部实现。

共享的仅是：

- 用户身份；
- GoTube 用户 ID；
- 同站入口组织。

## 认证方案

### 总原则

GameHub 复用 GoTube 认证，不复用 GoTube 业务存储。

### 推荐行为

1. GameHub 启动时，通过 GoTube 已有认证接口获取当前用户；
2. 已登录时，使用 `gotube_user_id` 作为用户关联键；
3. 未登录时，GameHub 以游客模式运行；
4. GameHub 不保存 GoTube 密码，不直接访问 GoTube 数据库。

### 最小必需字段

GameHub 侧需要的用户信息仅限：

- `id`
- `username`
- `role`

其中核心关联字段是 `id`，在 GameHub 侧对应 `gotube_user_id`。

### 失败回退

当 GoTube 用户状态接口不可用、返回 401 或网络异常时：

- GameHub 不应阻塞整个平台启动；
- 应回退为游客模式；
- 后续登录态恢复后再刷新平台身份。

## 首页设计约束

### 设计目标

首页不是营销页，而是应用门户。

必须满足：

- 一眼看出这是“统一入口站”；
- 两个应用入口都可直接进入；
- 后续继续增加入口时，不需要改动整体结构；
- 保留一块用于简短状态或说明的区域，但不应盖过入口本身。

### 结构建议

首页推荐结构：

1. 顶部站点头部
   - 站点名
   - 当前用户状态
   - 站点级操作入口
2. 应用入口区
   - 使用可扩展入口卡片或入口列表
   - 首批显示 `GoTube` 与 `您吉祥`
3. 底部简要说明区
   - 只保留必要说明，不写成长文案

### 入口数据模型

门户首页不应把两个入口写死在模板字符串中，而应抽象为统一入口配置，例如：

- `key`
- `display_name`
- `path`
- `description`
- `status`
- `kind`
- `icon/image`

这样后续接入第三个、第四个入口时，只扩入口配置，不重写整页结构。

## 接入方案

### 推荐方案

采用“GoTube 门户承载 + GameHub 独立部署”的方案。

具体表现为：

- GoTube 提供主页门户；
- `/ninlucky/` 指向独立的 GameHub 服务；
- 通过同域反向代理完成统一入口体验；
- GoTube 与 GameHub 继续独立构建、独立发布。

### 不推荐方案

#### 方案 A：直接把 GameHub 源码并入 GoTube 仓库

问题：

- 构建链耦合；
- 发布链耦合；
- 问题排查边界变差；
- 后续双方演进速度不同步时成本很高。

#### 方案 B：主页只放外链，不做同站接入

问题：

- 统一门户价值不足；
- 登录态体验割裂；
- 后续增加更多入口时难形成站点结构。

#### 方案 C：首页使用 iframe 嵌入 GameHub

问题：

- 路由、认证、主题和交互边界都容易变脏；
- 适合演示，不适合正式版本。

## 部署方案

### 生产推荐形态

- `gotube`：GoTube 主站服务
- `ninlucky`：GameHub 独立服务
- `nginx`：统一入口与路径转发

推荐代理关系：

- `/` -> GoTube
- `/ninlucky/` -> GameHub

### 优点

- 入口统一；
- 服务隔离；
- 构建独立；
- 问题排查清晰；
- 后续还能继续挂更多应用。

## 对现有 GoTube 的影响

### 直接影响

- 根路径页面将被重做为门户首页；
- 原 `index.html` 语义变化；
- 站点从单业务入口变成多应用入口。

### 不应改变的内容

- `/{hidden_path}` 下载入口不改；
- `/{hidden_path}/admin` 后台入口不改；
- `/watch` 分享播放不改；
- 现有多用户视频库与后台逻辑不改。

## 风险与控制

### 风险 1：首页改造影响既有访问路径理解

控制：

- 保持下载入口与后台入口稳定；
- 首页只做门户，不混入旧下载页行为。

### 风险 2：GameHub 与 GoTube 认证边界不清

控制：

- 文档里明确只共享身份；
- 不共享业务表；
- 只传 `gotube_user_id`。

### 风险 3：后续新增入口时首页再次重构

控制：

- 首版就引入统一入口配置模型；
- 页面结构按“可扩展入口列表”设计。

### 风险 4：部署复杂度上升

控制：

- 坚持独立服务 + 反向代理；
- 不在 V5.0.0 首版做源码级仓库合并。

## 验收标准

V5.0.0 门户方案落地后，至少满足：

1. 访问 `/` 能看到统一入口首页；
2. 首页能进入 `GoTube`；
3. 首页能进入 `/ninlucky/` 且展示名为“您吉祥”；
4. `/{hidden_path}`、`/{hidden_path}/admin`、`/watch` 仍保持可用；
5. GameHub 在已登录与游客两种状态下都能正常进入；
6. 后续新增入口时，不需要推倒重做首页结构。

## 建议实施顺序

1. 先完成 GoTube 门户首页骨架；
2. 再接入 `/ninlucky/` 路由与门户入口；
3. 再完成 GoTube 与 GameHub 的认证联动收口；
4. 最后补部署与联调文档。
